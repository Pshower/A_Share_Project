## 2. 影响"照着做"的问题

### 2.1 [P0] 持有日仍给出差额，页面还写着"差额为 0 才不需要下单"

**实测（2026-11-13 收盘，paper）**：

```
risky target 55.49%  now 59.64%  drift -4.15%  band 5%  -> hold
510300 +100   510500 +500   513500 -1,600   511010 0
```

引擎在 `hold` 分支（`tools/daily_allocation.py:130-137`）用 `risky_now` 反推目标权重，
于是 `plan_orders.orders()` 算出的 `delta` **全部是整手取整的残余**，`apply()` 在 `hold` 时一笔都不写
（`:215` 只在 `action == "rebalance"` 时下单）。但页面：

- 小标题是 `web/src/ExecutionPage.tsx:371`：**"整手 100 份；差额为 0 才不需要下单"**；
- `:394` 把 `delta` 原样渲染成 `+100 / −1,600`。

也就是说，**后端说"别动"，前端说"差额不为 0 就要下单"**。这一行名义金额约 **7,917 元**、
佣金 **15 元**；若每天照做，仅佣金就是 `15 × 242 / 1,000,000 ≈ 0.36%/年`，还没算价差——
对 4.4% 的预期收益是**十分之一**。

**修法**（后端优先）：

1. `hold` 时把 `delta` 全部置 0，另存 `rounding_delta`；`sleeves` 只保留目标份额供参考。
2. 页面在 `action === "hold"` 时把"差额"列显示为"—（取整漂移，不成交）"，并把小标题改成
   "只有**需要调仓**时，差额才是订单"。
3. 给 `apply()` 加一条断言：`action == "hold"` 时 `sleeves` 里不允许有 `delta != 0` 的行。

> **为什么是 P0**：这不是"少写一句提示"，而是**页面主动教用户做一笔引擎不会做的交易**。
> 资金量不大，但它正好发生在"最不需要操作"的日子，是用户最可能照做的一天。

### 2.2 [P0] 载体表：两笔漏记分红让"选错载体白丢 0.58pp"不成立

`doc/fund_vehicles_20261115.md` §3.1 的结论是：
**510300 −0.42 vs 159919 −1.00，差 0.58pp，选错载体白丢 0.58pp/年**。
我按"同日指数没动、基金却大跌"筛了一遍，发现两笔**新浪分红表里没有、但确实发生了**的除权：

| 代码 | 日期 | 基金跌幅 | 同日指数 | 隐含每份分红 | 说明 |
| --- | --- | ---: | ---: | ---: | --- |
| `510500` | 2022-08-29 | **−12.74%** | 中证500 **+0.20%** | **0.92** | 仓库自己的 `plan_backtest` 文档头也写过这笔（"the interface reports as 0.000"） |
| `159919` | 2019-01-14 | **−10.09%** | 沪深300 **−0.85%** | **0.344**（推断） | 同日指数只跌 0.85%，缺口几乎全是分红；金额按缺口推断，待公告确认 |

把这两笔补进 `paid` 后重算（其余口径、窗口不变）：

| 代码 | 报告值 | **补分红后** | 变化 |
| --- | ---: | ---: | --- |
| 510300 | −0.42 | −0.42 | 0 |
| `159919` | **−1.00** | **−0.23** | +0.77 |
| `510500` | **−0.99** | **+0.06** | +1.05 |
| 511010 | −1.03 | −1.03 | 0 |
| 513500 | −1.22 | −1.22 | 0 |

两件事因此不成立：

1. **"选错沪深300载体白丢 0.58pp"是假的**。补分红后 510300（−0.42）比 159919（−0.23）**还低 0.19pp**，
   方向反了。最终规格 §1 的载体列、§6 的"换载体"触发条件、README 第 52 行都引用了这个结论。
2. **510500 的 −0.99pp 也基本是假的**：补分红后是 **+0.06pp**，即跟踪差接近于零。
   （`510500` 的 0.92 有仓库自己的模块注释与精确缺口双重支持；`159919` 的 0.344 只有缺口推断，
   所以第 1 条的方向以"两者大致相当"为准，等公告确认后再定谁高谁低。）

**修法**：不要再"按跌幅推断分红"，也不要"完全不信推断"。建一张**显式白名单**
`configs/ex_rights.csv`（日期、代码、每份金额、来源、确认人），
`price_and_payouts` 只认"官方表 ∪ 白名单"；白名单之外的 ≥10% 跌幅一律**留作真实下跌**并打印出来。
这样 2025-04-07 的暴跌不会被抹平，2022-08-29 的分红也不会被丢掉。

### 2.3 [P1] 回测账仍少记一笔真实分红；`1,582,725.46` 不是真值

`24c125d` 把 `reports/account/backtest` 重导了：终点从 `1,687,442.92` 降到 `1,582,725.46`，
假分红 `2025-04-07 / 23,389` 没有了——这一半是对的。但同一套 `price_and_payouts`
现在把 §2.2 的 `2022-08-29 / 0.92` 也当成了真实下跌：

- 重导后的账本 17 笔分红里**没有** `2022-08-29`；
- 同窗口、同代码，只把这笔 0.92 加回去：2019-01-02 账本 **1,576,794.56 → 1,601,535.81（+24,741，+1.57%）**；
- 我的同窗口 129 起点：中位 **4.33% → 4.54%**、最差回撤 **−8.24% → −7.94%**；
  按官方基线加回同一效应（+0.207pp）则约为 **4.43% → 4.64%**。

官方书 `1,582,725.46` 与我的基线 `1,576,794.56` 差 5,931 元，来自窗口（11-13 vs 11-11）与分红时点；

> 假分红 2025-04-07（23,389）确实该删；但 2022-08-29 的 **0.92/份（14,444 元）** 该补，

### 2.7 [P1] 溢价熔断只在研究里，没进建议

`doc/etf_premium_20261114.md` 的结论是：513500 的溢价中位 4.00%、p95 **9.52%**、**2024 年后** 72% 的交易日 >2%；
"别买溢价"的硬闸门不成立，但建议 **仅在 ≥95 分位（≈9.5%）时拒绝加仓**，并把当时溢价记进成交。
现在 `tools/daily_allocation.py` 里**没有任何溢价字段**（`grep premium` = 0），
而 513500 占净值 30%。也就是说：研究写下的那条熔断，**在执行路径里不存在**。

**修法**：`recommendation()` 调 `etf_premium` 的净值序列（本地缓存即可），
返回 `premium` 与 `premium_blocked`；≥阈值时把 513500 的**新增买单**置 0、写进 `warnings`，
并让 `apply()` 把 `premium` 记进成交行。研究测算（8% 阈值下）"挡掉 5.6% 的交易日、避免约 3.8% 的净值损耗"，
那正是它值得接进执行层的理由。

```
-> 通过；ledger.use('live') 被调用
```

`tools/daily_allocation.py:209` 直接 `ledger.use(result["book"])`，而 `live` 是合法账户；
CLI 也仍然接受 `--book=live --apply`。所以"永远不会"依赖的是**调度任务的提示词**，
不是代码。这正是第一不变量最不该依赖的东西。

**修法**：`apply()` 开头 `if result["book"] == "live": raise ValueError(...)`；
真要支持，必须走 `--confirm-live` 且 `source="manual"`，并在报告里标红。

### 3.2 [P0] `feature_audit` 的目标是 Z-score 相除，96 行 IC 全部作废

`tools/feature_audit.py:114-116`：

```python
close = panel.pivot_table(..., values="close")
forward = close.shift(-horizon) / close - 1.0
```

而 `data/clean/all_stocks_features.parquet` 的 `close` **不是价格，是逐日横截面标准化的值**：

- 每日均值 ≈ 0、每日标准差 ≈ 1（`std` 中位 1.00，范围 0.43–1.56）；
- 全样本最大值 **16.1**（2021-02-10，600519）；
- 同一只股票（600519）2017 年初的 z 是 1.86、2024 年底是 10.5——z 的比值不是收益率。

所以 `close.shift(-h)/close - 1` 是**两个 z 相除**：分母可以为负、可以接近 0，
结果既不是收益、也不单调于收益。

**精确检验**（不依赖任何反解）：1 日的前瞻收益就是"下一个交易日的 `pct_chg`"，
而 `pct_chg` 的**秩**在任何仿射变换下不变。于是：

```
mean IC( rank(pct_chg_t), rank(pct_chg_{t+1}) ) = -0.0277   （1,942 个交易日，NW(1) t = -6.75）
```

这与仓库自己在 11-06 测到的 1 日反转（`body_ratio` **−0.0258 / t 5.69**、full 窗口 **−0.0272 / t 7.01**）同一量级；
而审计报告给的是 **+0.0095 / t 4.46**——**符号相反、量级 3 倍**。

**后果**：

- `doc/feature_audit_20261115.md` §0/§2/§7 的 **"0/96 过门槛"、"最强 0.0095"、"量价不值得再开"** 全部不成立；
- `doc/README.md:48` 的同一条结论也是；
- 这不是"效应弱"，是**目标变量被换掉了**。审计有机会在跑数前用"下一个 `pct_chg`"做一次自检，
  5 行代码就能发现符号翻了。

**修法**：`cross_sectional_ic` 的目标改成"下一日 `pct_chg` 的秩"（h=1）
或"从原始价面板重建的 h 日收益"（h>1），并在输出里存目标序列的来源与哈希；
重跑后**重新判断**量价家族，不要沿用"0/96"。

### 3.3 [P1] 日历"缓存"实际每次都联网，异常落在 `try` 之外

`tools/trading_calendar.py:33` 的刷新条件是 `dates.max() >= today + 365`。
新浪只发布到 **2026-12-31**，而今天是 2026-11-16，`today+365 = 2027-11-16`——条件永远为假，
于是**每次 `load()` 都重新下载 8,797 行**（实测 0.29–1.14 s/次，CSV mtime 每次都变）。
一次 `daily_ops` 会调用 **3 次左右**（`run` 的交易日闸门、`apply` 的过期判断、`is_month_open`）。

更麻烦的是位置：`tools/daily_ops.py:96` 的 `is_trading_day` 在 `try`（`:101`）**之前**。
新浪一挂，异常直接抛出 `run()` → `main()` 无捕获 → **退出码 1、没有 SUMMARY、没有
`reports/runs/daily_ops/<日期>.json`**。而调度任务的约定是"退出码 2 = 失败，去读那个 JSON"。

**修法**：`HORIZON` 改成 30–60 天；把日历判断包进 `try`，失败按 `status=failed` 记录并退出 2。

### 3.4 [P1] `daily_ops` 每天刷新 9 只载体

`tools/daily_ops.py:35` 遍历 `fund_vehicles.CARRIERS`（9 只），
而当日决策只用 `510300 / 510500 / 513500 / 511010`（`cash_safe` 时加 `511880`）。
多出来的 `159919 / 511260 / 511090 / 518880` 每天各拉一次行情与分红；
**任何一只失败都会让整轮 failed**——一只与当日决策无关的黄金 ETF 断网，paper 当天就不落账。

**修法**：`refresh_prices(codes)` 只刷当日需要的 4–5 只；其余留给手动的 `fund_vehicles --refresh`。

### 3.5 [P1] `audit_marks` 仍按后缀判 open

`tools/audit_marks.py:102`：`frame = opens if source.endswith("open") else closes`。
`unified_open` 是 `daily_allocation.apply()` 写的**收盘价**开仓单，却会因为后缀是 `open` 被拿去和**开盘价**比，
报一条不存在的"fill price does not match the open"。
现在 live 不再自动落账，但 paper 用 `--apply` 开账仍会产生 `unified_open`，所以这条路径还活着。

**修法**：不要猜后缀，维护 `source -> field` 的显式映射；未知来源按"不可核"列出，不要按名字推断。

## 4. 我复核后认为**没问题**的三件事

审查不能只报坏消息。以下三件我原本怀疑、实测后撤回：

### 4.1 同日收盘成交 vs 次日开盘：不是主要偏差

上一轮把"当日收盘出信号、当日收盘立即成交"列为 P1 并"按计划延后"，理由是"会改动最差回撤 −8.24%"。
我按真实 OHLC 跑了三个变体（129 起点、同一套费用与滑点）：

| 变体 | 中位年化 | 最差回撤 | ≥7% 起点 |
| --- | ---: | ---: | ---: |
| `close_inline`（现行） | 4.33% | **−8.24%** | 3.1% |
| `next_open`（收盘决定、次日开盘成交） | **4.63%** | **−8.29%** | 7.0% |
| `next_close`（次日收盘成交） | 4.72% | −8.30% | 6.2% |

**结论：影响在噪声内**（回撤差 0.05pp，收益反而高 0.3pp）。
"决定在收盘、成交在次日开盘"可以写进实盘流程，**不需要为此重做回测**。
限制：未模拟涨跌停、停牌、部分成交；开盘价来自新浪 OHLC。

### 4.2 账本的不变量是真的

抽查了 `replay` 唯一真相源、封存账拒绝 `mark`、过期报价拒写（代码与测试都点名到腿）、
四腿闸门（含国债腿）、`book()` 先全量干跑再落笔。**上一轮报的这几项确实修到位了**，
`tests/conftest.py` 的"测试写真实账本就判失败"守卫也还在。

### 4.3 "12 条候选 0 条通过 / 10% 是样本结论"是诚实的

`summary_daily.json`：C1 6.17% / −13.74%、E1 6.33% / −10.35%、E5 5.65% / −9.77%，
与 `unified_strategy_20261115.md` 第 4.1 节一致。**没有为了好看而改判据**，这一点值得保留。
