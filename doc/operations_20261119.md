## 2. 2027-01-04：如果数据源没跟上，从那天起每天失败

`trading_calendar.is_trading_day` 在日期超过缓存末日时**选择抛错而不是回答"休市"**（`tools/trading_calendar.py:76-78`），这个设计是对的：静默回答 False 会让每日任务安静一年。

问题是缓存末日就是**数据源的末日**。今天实测：

```
calendar source: 8797 rows, max=2026-12-31, 0.81s
is_trading_day("2027-01-04") -> ValueError: trading calendar ends 2026-12-31, before 2027-01-04; refresh it
```

它并不是死路：`load()` 在缓存盖不住今天时会**先尝试刷新**（`trading_calendar.py:39-59`），所以只要那天 akshare 已经能返回 2027 年的日期，缓存会被就地更新，任务照常跑。风险恰好在"如果没更新"：

- 交易所通常在 12 月公布次年安排，但没有任何东西检查它有没有发生；
- 一旦没更新，失败是**全面**的——`daily_ops.run` 记 `failed`、退出码 2、写失败 JSON，不出建议、不记账、也不生成曲线；
- 失败从 2027 年第一个交易日（1-04，距今 **46 天**）开始，而缓存在 **12-31**（42 天后）就已经是最后一天。

三个动作，按性价比排：

1. **摘要里显示剩余天数**（10 行）：「日历剩 N 天」只在 N < 60 时出现。这样 11 月底就能看见 42 天这个数字，而不是等到 1 月 4 日。
2. **12 月的一次检查**：随便哪天跑一次 `python -m tools.trading_calendar --refresh`，确认 `calendar_last` 已经进入 2027。
3. **不要加"工作日兜底"**：在 2027 年的元旦/春节假日让模型下单，比停一天糟得多。
